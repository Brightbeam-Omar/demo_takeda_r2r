# F21 · Sync Status, Webhook Sync Status & Admin Pages

## Context
This brings the operational and admin pages to parity. **Sync Status** lists every pipeline load. **Webhook Sync Status** shows the health of the trigger queue, with health cards and action buttons. The ADMIN menu items get real or clearly labelled placeholder pages. It replaces F11's single Sync page.

## Functional requirements
| ID | Requirement |
|---|---|
| F21-FR-01 | **Pipeline runs (fact):** the pipeline publishes `pipeline_runs_v` (the last 100 runs from `intelligence.pipeline_run_log`, with each run's previous failures included): `pipeline_run_id, started_at, duration_ms, files` (number of source tables/files extracted), `inserted` (rows in `batch_pipeline_v` whose content hash differs from the previous successful snapshot, or are new), `total` (rows after the run), `skipped` (`total − inserted`), `status` (`ok`/`failed`), and `failed_step` (null if ok). Because a failed run publishes nothing, its row first appears in the next successful run's `pipeline_runs_v`. Content hash: a stable hash over the 04 §4.1 business and fact columns **excluding `snapshot_date`, `run_id`, `published_at`** (listed explicitly in code), computed in `snapshot_aggregate` via a shim `row_hash()` (test per dialect). The previous hashes live in `intelligence.row_hash_last` (`row_key, row_hash, pipeline_run_id`), read **before** the snapshot partition is replaced, so same-day re-runs compare correctly. Each row also carries `run_id` = the publishing run. Also publish `pipeline_run_steps_v` (`pipeline_run_id, step, status, started_at, finished_at, rows, error, run_id`). Both objects join `OBJECTS_WITH_RUN_ID`. Mirrors `mirror_pipeline_runs` and `mirror_pipeline_run_steps` |
| F21-FR-02 | **Sync Status page** (`/admin/sync`): title "Sync Status", subtitle "History of every pipeline run — click a Run ID to see per-step detail". A `DataTable` with these columns: Run ID (link → a window with the per-step rows from `mirror_pipeline_run_steps`: step, status, duration, rows, error), Started (relative age, OQ-054), Duration, Files, Inserted, Total, Skipped, Status (OK green / FAILED red with the failed step beneath). Sorted newest first. Export. A link "Open in Dagster" per run (`VITE_DAGSTER_URL`) |
| F21-FR-03 | **Webhook Sync Status page** (`/admin/webhooks`): six cards — **Last Webhook Received** (age), **Pending Events** (`status=pending`), **Error Events** (`failed`), **Abandoned Events** (claimed and older than `STALE_CLAIM_MINUTES` (5), or `attempts ≥ 2`), **Safety-Poll Fallbacks (24h)** (`source=poll` count; shows `0` with a "T2-02" tag until the poll exists), **Last Drain** (age of the worker's last loop). In normal running the middle four read 0, styled with a green top bar; non-zero is amber/red |
| F21-FR-04 | **Event list:** `DataTable` with these columns: ▸ expand · Received (age) · Source · Run ID · Status · **Attempts** · **Views Synced** (new `sync_event.objects_synced`) · Rows Upserted · Duration. The expanded row shows the drain pass id, claimed/finished ages and any error. Add `sync_event.attempts` (incremented on each claim) and `drain_pass_id`. Add a new `worker_heartbeat` table (`worker_id, last_loop_at, last_pass_id`) updated every loop |
| F21-FR-05 | **Buttons:** `Refresh` (refetch; any role); `Trigger Sync Now` (admin: new `POST /api/sync/run-pipeline`, where app-api proxies to scenario `POST /pipeline/run` with `SCENARIO_TOKEN`, audit `pipeline_triggered`, and then the webhook flows as usual); `Drain Queue Now` (admin: the **existing** `POST /api/sync/trigger`, which inserts a `manual` event; the worker additionally wakes every 2 s to check for pending events). Both admin actions confirm first ("This starts real work that affects everyone's view") and write audit events (`pipeline_triggered`, and the existing `sync_triggered`) |
| F21-FR-06 | **Admin pages:** **Team Dashboard:** per owning team (from the stage reference), open rows, late rows, the oldest late (days over), and the share at risk (amber), each team row linking to the Overview filtered to its stages. **Audit Log:** F11's page moved under ADMIN. **Schema Reference:** the published contract as a browsable list of each object with its description, grain and columns (name, type, description), served from a committed `contract.json` generated from `04-data-contracts.md` by a script, with a CI check that it's in sync. **SLA Configuration:** a read-only table of stages (label, SLA, re-eval SLA, team, card shown) and metrics (entry, exit, SLA, window), with the note "Configured in the site profile `<active profile file>`; changes take effect at the next pipeline run". **Feedback:** the F15 list. **Upload Data, Process / Campaign Mapping, POC — Integrations and Configuration:** placeholder pages titled per the menu, each with a one-paragraph description of the intended capability and a "Tier 2" tag (Upload Data → T2-07 spreadsheet ingest) |
| F21-FR-07 | Remove the deprecated F09/F11 status and comment endpoints (superseded by the F19 status log) and the old `/sync` route (redirect it to `/admin/sync`) |

## Decisions (OQ-129 to OQ-135)
- **OQ-129:** a failed run shows "—" for `inserted`, `total` and `skipped`; `row_hash_last` is written only by successful runs, after the comparison; AC-01 is tested without a clock move.
- **OQ-130:** Abandoned counts only events still `claimed` (stale, or `attempts ≥ 2`); Error counts `failed` only.
- **OQ-131:** the worker wakes every 2 s, runs a full pass every `DRAIN_INTERVAL_SECONDS` and writes the heartbeat on every wake; a manual event shows "—" for Run ID.
- **OQ-132:** column types come from the pipeline's Delta schemas, descriptions from 04 §3 plus `specs/contract_descriptions.yaml`; `contract.json` is copied into the app image; CI regenerates and diffs it.
- **OQ-133:** Team Dashboard = snapshot, open = not released and not pending, late = RAG red, at-risk = amber ÷ open; ignores filters; rows link to `/overview?stage=…`.
- **OQ-134:** the entry/exit lookup lives in the API keyed by stage; `/api/reference` gains `profile_file`.
- **OQ-135:** Feedback is the last ADMIN item; Audit Log at `/admin/audit` (`/audit` redirects); run ages use the demo clock, event ages wall-clock, each stated in a tooltip.

## Acceptance criteria
- **F21-AC-01** After two `make pipeline` runs on unchanged data, the second run shows `inserted = 0` and `skipped = total`. After a scenario event that changes one lot, the next run shows `inserted ≥ 1`.
- **F21-AC-02** Forcing a failed run (fixture) produces a FAILED row with `failed_step` after the next successful run.
- **F21-AC-03** Webhook page cards at rest: Pending 0, Error 0, Abandoned 0, and Last Drain < 30 s ago. After stopping `app-worker` and triggering a pipeline, Pending becomes 1 and Last Drain ages. Restarting it clears both.
- **F21-AC-04** As Admin, Trigger Sync Now creates a pipeline run, then a webhook event, then `done`, all visible on both pages. As Sam, the buttons are disabled.
- **F21-AC-05** Team Dashboard: the late counts per team sum to the Overview late count.
- **F21-AC-06** Schema Reference lists every published object. The CI check fails if `contract.json` is stale.
- **F21-AC-07** Screenshots `docs/screenshots/{sync,webhooks,team,schema,sla-config}.png`.
